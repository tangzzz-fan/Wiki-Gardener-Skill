# 园艺审计（Gardening）

定期全局健康检查。频率默认双周，或用户报告"感觉乱了/有重复"时立即触发。

## 1. 审计主流程与操作顺序

```
冗余扫描 → 去重处理 → 偏离分诊 → 腐烂扫描 → 漂移报告
→ 汇总人话摘要 → 用户逐项确认 → 执行 → 写日志 → 指标记入 Atlas
```

**操作顺序铁律**：先去重合并 → 再偏离分诊（迁移/拆分）→ 最后才做单篇提炼。先润色后合并等于给即将消亡的笔记抛光，全部返工。

## 2. 冗余扫描与去重协议

运行脚本获得重复簇：

```bash
python3 scripts/dup_scan.py <vault路径> --threshold 0.7
```

按簇内相似度分四类处理：

| 相似度 | 判定 | 动作 |
|---|---|---|
| > 0.95 | 完全重复 | 保留信息更全者，副本归档 |
| 0.85–0.95 | 近似重复 | 走合并协议（下述） |
| 0.7–0.85 | 互补重叠 | **不合并**：抽公共部分为第三篇原子笔记，两篇互链它 |
| < 0.7 | 同主题不同深度 | 保留，MOC 中分层标注（基础/进阶） |

**合并协议**（L3，永远人工批准）：
1. 选正本：按完整度、时效性、被链接次数、宪章对齐度打分，最高者为正本，其余为供体
2. 提取每篇供体的独有段落，列清单进诊断单
3. 将碎片整合进正本
4. 供体移至 `90_archive/`（不删除），全库指向供体的链接重定向到正本
5. 更新 MOC，写决策日志（含正本选择理由）

## 3. 腐烂扫描

检查时效性，按域进行：
1. 加载 `00_系统/domains/` 各域档案的时效性锚点（当前系统/API/框架版本）
2. grep 全库中的版本号、API 名，比对锚点
3. 无域档案的主题标注"未核验"，不猜

处理分级：
- 事实性错误（API 已废弃且笔记在推荐它）→ correct 诊断单，优先处理
- 部分过时 → 笔记顶部加 frontmatter `stale: true` 与过期说明，排队修订
- 完全过时且无保留价值 → 归档（L3，需批准）

## 4. 漂移报告

回答一个问题：**知识库是否在朝宪章的北极星走？** 检查项：

| 检查项 | 计算 | 异常信号 |
|---|---|---|
| 各域增长率 | 本期新增笔记按域分布 | 某域暴涨且与北极星无关 = 主题漂移 |
| 域荒废 | 各域最后更新时间 | 核心域 > 4 周无更新，问用户是否计划如此 |
| 孤儿率 | 零入链笔记 / 总数 | > 10% 说明吸附挂载在失败 |
| inbox 滞留 | inbox 内文件平均停留天数 | > 3 天说明吸附流程卡住 |
| 重复率趋势 | 本期重复对数 vs 上期 | 上升说明入口端判重在失效 |

异常项全部转化为人话问题问用户（例：「某核心域三周没新内容了，是计划如此吗？」），而非自作主张调整。域名来自用户 vault，不预设行业。

## 5. 审计摘要格式

输出给用户的是人话摘要，不是原始报告（禁止 emoji）：

```
花园巡查（YYYY-MM-DD）
- 发现 3 组内容重复，建议合并（最严重的：《A》和《B》91% 重叠）
- 2 篇笔记引用的接口/版本已相对域档案锚点过时
- 「域甲」增长很快，「域乙」三周没动静——是计划如此吗？
- inbox 里有 4 份东西躺了超过 5 天

[逐个处理]  [只看重复的]  [全部忽略]
```

用户确认后逐项走诊断单流程执行，全部写日志，指标记入 `00_系统/atlas/健康基线.md` 与上期对比。
