# Persona：iOS 原生与跨平台工程师

> 适用画像：以 iOS 为主、同时涉猎 Flutter/RN/KMP 的移动端工程师，
> 每年被 WWDC 追着一个周期跑，跨平台选型是反复出现的决策场景。
> 用法：setup-wizard 第零轮选中本 persona 后，预填项降级为确认题——
> 展示给用户改，而不是让用户从零写。**北极星必须用户亲口确认，persona 只给候选。**

## 北极星候选（供用户修改）

- 「三年后这个库是我的移动端技术资产：每个 API 坑、每次选型依据都可查，不随换工作清零」
- 「WWDC 每年砸下来的新东西，进这个库就变成我自己的判断，而不是收藏夹尸体」

## 收录标准种子

- 收：API 踩坑记录（必须带系统版本与机型环境——移动端坑高度依赖环境）
- 收：跨平台 vs 原生的真实项目对比（性能数据、包体积、团队成本）
- 收：WWDC 新能力的跟踪判断（要不要跟进、何时跟进、对现有架构的冲击）
- 收：性能优化记录（含优化前后数据，无数据不收）
- 收：能**深入本质**的笔记——用**第一性原理**拆到平台约束与机制（例如：主线程、内存模型、桥接成本、渲染路径），不只记 API 用法
- 不收：官方文档和 Release Notes 的抄写
- 不收：没有真机验证的"跨平台性能对比"搬运文
- 不收：已废弃 API 的 workaround（归档而非正文保留）
- 不收：只有步骤/术语清单、未追问本质的操作备忘

## 笔记类型模板

> 工程师笔记底线：每张卡至少有一句「本质/约束」层——用第一性原理回答「为什么」，禁止只留步骤。

- **踩坑卡**：现象 / 系统版本+机型 / 根因 / 解法 / availability 检查项 / **第一性原理一句**
- **WWDC 跟踪卡**：新能力 / 废弃了什么 / 对现有代码的冲击 / 跟进决策与时机（须答「跟进或不跟进的硬约束是什么」）
- **性能记录卡**：指标基线 / 优化手段 / 优化后数据 / 回归风险
- **选型对比卡**：需求约束 / 原生 vs Flutter vs RN vs KMP / 实测 / 结论与边界

## 推荐 Atlas 分区（总 MOC 主题骨架，不是文件夹）

> 笔记平铺在 `20_领域/`；分类只写在总 MOC。勿建 `iOS/`、`Flutter/` 实体子目录。

| MOC 分区 | 放什么 |
|---|---|
| iOS 踩坑与 API | 版本绑定的坑、availability、真机结论 |
| WWDC 与跟进决策 | 新能力跟踪、跟进/不跟进的硬约束 |
| 性能与 Instruments | 基线、优化、回归风险 |
| 跨平台选型 | 原生 vs Flutter/RN/KMP 对比 |
| 客户端架构 | 状态管理、模块边界、逃生舱 |

命名约定候选：`系统版本-主题-结论.md`（例：`iOS17-扫描过滤-后台策略.md`）。

## 协作边界种子（须用户确认）

| 项 | 候选问法 | 落盘 |
|---|---|---|
| 最低支持版本 | 「现在最低 iOS / 是否已上 SwiftUI 为主？」 | iOS开发 · 时效性锚点 |
| 跨平台占比 | 「原生与跨平台大概比例？」 | 跨平台开发 · 局部宪章 |
| AI 权限 | 确认：助手给方案与审查，发版决策你拍板 | 宪章旁注 |

## 访谈变体（第零轮选中后替换默认问题）

- Q4 替换为：「发我一个你最近踩过的移动端坑，或者一次选型纠结的过程——最好能说到机制层，而不只是『换个 API』」
- Q5 替换为：「跨平台内容你想记到什么深度？（比如：只记决策结论 / 用第一性原理拆到引擎与桥接成本）」
- Q7 追加：「你现在的项目里原生和跨平台的比例是？团队还是自己开发？」——决定两个域的加载优先级

## 度量权重

- 重点盯 **腐烂扫描**：以 WWDC 为年度节律，每年 6 月后全库锚点必须巡检
- 其次盯 **孤儿率**（移动端笔记容易按技术点孤立记录，挂不进项目上下文就白记）
- 抽查笔记是否仍停留在步骤层：若连续多篇缺少「为什么/约束」句，视为品味漂移

## 专家顾问团（辅助身份映射表）

> 以下身份不是独立 Agent，是挂在各域档案上的「专家立场」。
> domain-expert 在该域执笔/审查时读取立场，即成为该专家。召唤方式：对 Agent 说
> 「以 xx 专家的身份……」并确保对应域档案已加载。

| 场景 | 召唤身份 | 立场存放处 |
|---|---|---|
| iOS 方案审查、API 使用、WWDC 跟踪 | 资深 iOS 架构师 | `domains/iOS开发.md` |
| 跨平台选型、Flutter/KMP 方案 | 跨平台架构专家 | `domains/跨平台开发.md` |
| 客户端架构决策（Redux/Clean 等） | 资深架构评审委员会 | `domains/架构设计.md` |
