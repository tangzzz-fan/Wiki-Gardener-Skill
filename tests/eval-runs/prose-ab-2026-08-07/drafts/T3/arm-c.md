# 前提假设死了就 archive 再新写，别把草稿缝成文物

写给三个月后那个很忙的自己。一篇草稿的立论前提已经作废时，继续打补丁往往比新写更贵。默认动作是标 archive，再开一篇按当前前提写的新稿。硬改只留给前提仍活着、只是表述糟糕的情况。

## 一次缝补经历

换知识库结构之前，我写过一篇「MQTT QoS 选型」初稿。后来选型标准变了。关注点从「消息绝不能丢」，挪到「通道不稳时宁可丢遥测，也要保住命令通路的界别」这类新尺子。我改了两轮。每轮都在旧段落上贴条件句，读起来像补丁文物。旧结论还在，新例外叠上去，谁也说不清现在到底选 QoS 几。

成本不在打字。成本在每次打开都要重新解冲突。

## 可检查的丢弃信号

打开一篇久未碰的草稿，只问下面三句。命中两条以上，优先 archive。

文中写过「因为我们假设 X」，而 X 你现在已明确否定，或业务上已切换。前提句不再为真。

你记得自己为同一结论叠加过两次及以上「但是 / 除非 / 另外」，又从没重写过总领段落。补丁次数已经压过结构。

标题或首段结论，需要你当场编织才能说圆。正文已经不能代表此刻判断。

「写了多久算过时」没有固定天数，我也不编一个。[待核验] 是否要在宪章里约定，inbox 草稿超过 N 天未吸附就强制重读前提。此刻没有这个数字，别假装有。

## 丢弃之后做什么

把旧稿移到 `90_archive/`，或你库约定的 archive 路径。frontmatter 可留一行，写明被何种前提取代。

新开 inbox 稿，只写现在的前提与选型。需要历史时，链到 archive。不要把旧论证嵌进新正文。

旧稿里若还有仍然正确的原子段落，例如某一错误码释义，拆出来单独成篇，再链接。不要整份续命。

## 什么情况还该硬改

前提仍成立，烂的是结构或口语。缺例子，标题弱，某一节重复。这时硬改便宜。判别方法很简单。你动的是表述，可以硬改。你动的是当初为什么这么选，就已经接近该新写的阈值。

## 挂载建议

挂到总 MOC，或「库维护习惯」一类入口。若 [[MQTT QoS 选型]] 仍在领域里，互链时注明本篇只谈丢弃决策，不谈 QoS 内容本身。

我不为了显得勤快而救每一篇旧稿。勤快留给当前判断已经清楚的那一篇。
