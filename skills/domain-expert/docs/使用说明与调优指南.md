# domain-expert 使用说明与调优指南

> 配套文件：本目录上级为 skill 本体（或打包后的 `domain-expert.skill`，v1.1）
> 前置依赖：建议已部署 `wiki-gardener` 并完成知识库初始化（本 skill 可独立使用，但与园丁协作才发挥完整价值）
> 与同仓库 `skills/wiki-gardener/docs/使用说明与调优指南.md` 互为姊妹篇
> 开源总览与评测：仓库根目录 `README.md`、`tests/EVAL.md`（https://github.com/tangzzz-fan/Wiki-Gardener-Skill）

---

## 一、它是什么

domain-expert 是"领域专家"skill：以**你指定的任意领域**资深专家身份，提供两种能力——**执笔**（和你聊透一个主题后写成笔记初稿）和**审查**（对你写好的草稿做事实性审核）。领域由 vault 里的域档案定义，不绑定某一行业。

它管的是**单篇内容的质量（对不对）**，不管库的结构——"该不该收、放哪、重不重复"是 wiki-gardener 的职权。两个 skill 平级协作，诊断单 Schema 是通用语。

skill 内部结构（报错排查用）：

```
skills/domain-expert/
├── SKILL.md                    # 主入口：双模式路由 + 五条铁律
├── references/
│   ├── writing-mode.md         # 执笔模式：追问清单、库上下文读取、成文规范
│   └── review-mode.md          # 审查模式：核验清单、报告 Schema、分级处理
└── assets/templates/
    └── review-report.md        # 人话版审查报告模板
```

**五条铁律（理解这些就理解了这个 skill 的行为逻辑）：**
1. 产出永远进 `10_inbox/`，绝不直接写入 `20_领域/`
2. 产出必须标注 `origin: chat | draft` 和 `status: draft`
3. 写与审是两次独立执行，作者不校对自己的稿子
4. 审查产出结构化报告，不写散文式评语
5. 无对应域档案时，会明确告诉你"判断未经校准"

## 三、日常使用（两个模式）

### 模式一：执笔（聊主题 → 成文）

**触发说法**：「我想聊聊 BLE 配网这个主题，然后帮我写成一篇笔记」  
也可只丢零散思路：「想用插件模式做个 Swift 网络库」——写手应先追问再成文，不要求你事先往 inbox 丢文件。

流程与你要参与的节点：

```
① 对话追问  → ② 共识大纲（你确认）→ ③ 成文落 inbox → ④ 审查（你点头）→ ⑤ 整理 inbox 吸附
```

- **① 追问阶段是关键**：Agent 会问你踩过的坑、你的判断、不想讲什么。**认真回答这一步直接决定成文质量**——它写的是你聊出来的东西，不是替你编的。只丢一个题目就让它写，会得到一篇平庸的 AI 文摘
- **调教写手**：改 vault 里 `00_系统/domains/<域>.md` 的「写作立场」「执笔与审查协议」（见仓库 `docs/自定义与调教指南.md`），不必改 skill 源码
- **② 大纲务必过目**：确认标题结论是你的立场、边界（不写什么）划对了
- **③ 成文后**：检查文中的 `[待核验]` 标注（它不确定的事实会显式标出，宁可标注不硬写）
- 特殊情况：纯资料整理不需要你的观点时，明说「这篇不需要我的观点」，成文会标 `origin: reference`

**健康信号 vs 危险信号**：
| 健康 | 危险 |
|---|---|
| 对话占整个流程一半以上时间 | 你说一句"帮我写 xx"，它直接出全文 |
| 成文里有你的判断、你的坑、你的原话 | 成文工整但换成任何人的库都成立 |
| 它发现与已有笔记重叠，建议改旧文而非新写 | 每篇都新写，库越来越臃肿 |

### 模式二：审查（草稿 → 结构化审核）

**触发说法**：「以 iOS 专家身份审一下这篇」「inbox 里那篇草稿帮我审」

流程：

```
加载域档案 → 六项核验 → 人话摘要 + 分级报告 → 你确认 → 修订 → 转 seedling
```

核验六项：事实正确性 / 时效性 / 最佳实践偏离 / 常见误区命中 / 缺失项 / 执笔阶段遗留的 `[待核验]` 标注。

你会看到的输出：

```
审查结果：《示例主题》（<你的域>）
总评：整体成立，有两处需要修。
[高优先]（1）……  [中优先]（2）……  缺失：某边界条件
[按报告修订]  [逐条讨论]  [我自己改]
```

- verdict 四级：pass（可转 seedling）/ revise（修订后走吸附）/ major_revision（修订后复审）/ reject（极少用）
- 有 `[高优先]` 项时修订后会**自动复审一遍**，别跳过
- 修订完成且你明确确认后，`status: draft → seedling`，然后走吸附挂载
- 对人输出不使用 emoji（与 AGENTS.md 一致）

### 两个 skill 的协作顺序（重要）

**真实性先于结构性**：先审查（domain-expert），后吸附（wiki-gardener）。

```
写/投 → 审查（对不对）→ 修订 → 吸附（该不该收、放哪）→ 挂载
```

顺序反了会把事实错误的内容挂载进库再返工。日常说法就是：审完再说「整理 inbox」。

## 四、后续调优指南

按预期出现频率排序。

### 1. 域档案质量（最高频，决定两个模式的上限）

**症状**：审查抓不住领域错误、成文深度不对、时效性判断失灵。
**改法**：`00_系统/domains/<域>.md` 的三个节是关键——
- **时效性锚点**（当前版本号）：须随系统/框架发版手动更新，过期锚点 = 腐烂审查全部失准
- **常见误区**：每发现一个"这个领域大家容易写错"的点就补一条
- **写作立场**：成文风格不像你？改这里的"偏好写法/避免写法"

域档案是三个角色（园丁/写手/审查员）共读的唯一知识源，**改一处三方同时受益**——这是调优杠杆最大的地方。

### 2. 追问侵入度（执笔模式）

**症状 A**：追问太多太烦，你其实只想要快速整理。
**改法**：明说「这篇不需要我的观点，按资料整理写」，会跳过观点追问走 `origin: reference` 通道。
**症状 B**：追问太少，成文空洞。
**改法**：编辑 `references/writing-mode.md` 第 2 节，为你的常用领域加定制追问（如 iOS 域加「线上还是调试环境遇到的？」）。

### 3. 审查严格度（审查模式）

**症状 A**：报告全是吹毛求疵的低优先项，噪音大。
**改法**：告诉它「只报中优先以上」，或在 `review-mode.md` 把 severity 分级标准改严。
**症状 B**：放过了实质错误。
**改法**：大概率是域档案的误区清单/Smell 清单太薄——回写档案，不是改审查 prompt。

### 4. verdict 边界

**症状**：pass/revise/major_revision 的判定和你的体感不符。
**改法**：`review-mode.md` 第 3 节的判定规则是起点。积累 10–20 份报告后对照你的实际处理，校准 high/medium 的定义。

### 5. "写完直接审"的仪式感

**症状**：你让它写完直接审，审查报告却明显带着执笔时的思路（自卖自夸）。
**改法**：这是自审盲区的信号。分开两次调用：写完先放一放，新开会话说「审一下 inbox 里那篇」。技术上 skill 已要求审查时"清空执笔思路"，但物理隔离（两次会话）是最可靠的。

### 6. 来源占比监控（长期健康）

**症状**：担心 AI 生成内容稀释库的品味。
**改法**：园艺审计时按 frontmatter 的 `origin` 字段统计 `chat/reference` 占比。占比持续攀升 + 你的 approve 率下降 = 漂移信号，该收紧执笔的使用场景（回到"聊透才写"）。

## 五、边界与注意事项

| 事项 | 说明 |
|---|---|
| 不做挂载决策 | 审查通过 ≠ 应该收录。"内容正确但和库里重复"会被园丁拒收，这是正常协作不是矛盾 |
| 不联网核验 | 事实判断基于域档案 + 模型知识。高时效主题（刚发布的系统版本）须人工更新锚点后再审 |
| draft 阀门不可绕过 | 任何 `origin: chat` 的内容必须经你确认才转 seedling——这是防止库变成 AI 文摘站的核心阀门 |
| 对话内容的存档 | 执笔前的对话本身不进库（只有成文进）。想把讨论过程也留存，让它额外生成一份对话纪要笔记 |
| 跨领域内容 | 一篇横跨两个域的内容，以篇幅占比高的域为主审，另一域只取交集项核验 |

## 六、版本迭代建议

v1.1 → v1.2 最可能的修改点（按优先级）：
1. 域档案三个关键节的充实（随真实使用持续积累，**这是长期动作不是版本动作**）
2. 追问清单的领域定制（根据执笔模式的实际对话质量；对照 EVAL B3）
3. severity 分级与 verdict 边界（根据 10–20 份真实审查报告校准；对照 EVAL B1）
4. 人话摘要的详略（根据你阅读报告时的耐心临界点）

修改 skill 本体后跑结构校验与 EVAL，push 到 GitHub；用户侧 `npx skills@latest update -g -y`。Desktop 再 `./scripts/pack_skills.sh` 上传。域档案、决策日志在 vault 内，不随 skill 升级覆盖。
