# 审查模式

对草稿/部分材料做领域事实性审查。产出结构化报告，供下游编辑流程执行。

## 目录

1. 审查流程

3. 审查报告 Schema

---

## 1. 审查流程

```
确定域 → 加载域档案 → 逐项核验 → 出报告（JSON + 人话摘要）
→ 用户确认 → 编辑流程执行修订 / 用户自改 → 结论抄送吸附流程
```

姿态要求：**以第一次阅读的姿态进场**。即使内容是自己执笔模式写的，也不复用当时思路——作者不校对自己的稿子。

## 2. 核验清单

按优先级逐项检查，每项给出命中/未命中 + 证据：

| 项 | 检查内容 | 依据 |
|---|---|---|
| 事实正确性 | 概念定义、API 语义、机制描述是否成立 | 域档案 + 通用领域知识；存疑标 `[待核验]` |
| 时效性 | 版本号、API 可用性、框架推荐实践是否过期 | 域档案时效性锚点 |
| 最佳实践偏离 | 是否存在"能用但已非主流/有坑"的写法 | 域档案 Smell 清单 |
| 常见误区命中 | 是否落入该领域高频错误认知 | 域档案常见误区节 |
| 缺失项 | 主题是否缺了关键维度（如讲了用法没讲边界条件） | 专家判断；优先对照域档案「执笔与审查协议 · 审查必查」 |
| `[待核验]` 标注 | 执笔阶段留下的标注逐条裁决 | 能确认则确认，不能则保留并说明 |
| 交付契约符合度 | 若域有「执笔交付物」规范，成稿是否缺关键字段 | 域档案执笔与审查协议 |

无域档案时：仅做通用正确性检查，报告中注明"未经域档案校准"，并建议用户建档。有档案但无「执笔与审查协议」时：仍审，并提示用户按种子模板补协议节。

## 3. 审查报告 Schema

与 wiki-gardener 吸附诊断单对齐的机器层契约：

```json
{
  "target": "10_inbox/xxx.md",
  "domain": "ios",
  "verdict": "pass | revise | major_revision | reject",
  "findings": [
    {
      "type": "fact_error | stale | practice_deviation | misconception | missing | unverified",
      "severity": "high | medium | low",
      "location": "第 3 节 / 引用原文片段",
      "claim": "原文的说法",
      "correction": "正确说法或建议",
      "basis": "依据（域档案条目 / 通用知识 / [待核验] 存疑）"
    }
  ],
  "freshness_input": "ok | stale | error",
  "summary": "一句话总评",
  "confidence": 0.85,
  "requires_approval": true
}
```

verdict 判定：
- `pass`：无 high 级 finding——可转 `seedling` 并走吸附
- `revise`：有 medium 级——修订后走吸附
- `major_revision`：有 high 级——修订后需复审
- `reject`：主题本身不成立（极少用，须向用户充分说明）

`freshness_input` 字段专门喂给吸附流程，作为其诊断中 freshness 的输入——**真实性先于结构性**，审查通过的内容才进入挂载判断。

## 4. 人话摘要格式

JSON 是机器契约，给用户看的是这个：

```
审查结果：《标题》（<域> 域）
总评：整体成立，有两处需要修。

[高优先]（1）
1. 第 3 节「某关键参数默认值」——与域档案锚点不符，需修正。
   依据：域档案时效性锚点 / Smell 清单

[中优先]（2）
1. 某处推荐做法建议补充当前主流替代方案……
2. ……

缺失：没讲失败重试 / 边界条件，建议补一节。

[按报告修订]  [逐条讨论]  [我自己改]
```

人话输出禁止使用 emoji；优先级只用 `[高优先]` / `[中优先]` / `[低优先]` 文本标签。

## 5. 分级与后续处理

- 用户选"按报告修订"→ 调用编辑流程执行 correct/rewrite，修订后 high 级 finding 需复审一遍
- 用户选"逐条讨论"→ 进入对话，讨论达成的结论更新到报告再修订
- 修订完成 → `status: draft → seedling`（须用户明确确认），提示走吸附挂载
- 审查中发现的域档案缺口（如新的误区、过时的锚点）→ 提示用户回写域档案，**修档案而非只修个案**

## 6. 与吸附流程的衔接

审查完成后，向用户说明下一步的归属：

「事实层面这篇已经 OK。接下来挂载、查重是园丁的活——你说一声『整理 inbox』就走吸附流程。」

不越权做挂载决策；吸附流程若判定冗余/拒收，是独立结论，不与本审查冲突（内容正确 ≠ 应该收录）。
