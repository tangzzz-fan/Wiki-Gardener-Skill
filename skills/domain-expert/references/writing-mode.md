# 执笔模式

从"聊一个主题"到"一篇吸附原生的笔记初稿"。

## 目录

1. 阶段划分
2. 对话阶段：追问清单
3. 动笔前：库上下文读取
4. 成文规范
5. 交付与下一步

---

## 1. 阶段划分

```
对话聊透 → 共识大纲（用户确认）→ 读库上下文 → 成文 → 落 inbox → 提示审查
```

铁律：**对话优先于成文**。写手的价值是记录和结构化用户的判断，不是替用户思考。用户只给了一个题目就要求成文时，必须先进入追问。

## 2. 对话阶段：追问清单

目标是把用户脑子里的"活知识"挤出来。按此清单追问，一轮不超过 3 个问题：

1. **经验锚点**：「这个主题你实际踩过什么坑 / 做过什么决策？」——有真实经验的内容才是独一无二的
2. **立场与结论**：「你对它的判断是什么？有没有和主流看法不一样的地方？」——标题即结论，结论必须来自用户
3. **边界**：「这篇不想讲什么？和库里已有内容的分工是什么？」
4. **受众与深度**：「写给三个月后的自己看，还是写给同行看？」
5. **素材**：「有没有代码片段、日志、截图描述可以放进去？」

**跳过成文的信号**（满足其一才可动笔）：
- 用户明确给出了核心结论和至少一个经验锚点
- 或用户明确说「这篇就是知识整理，不需要我的观点」——此时按资料整理写法，并在 frontmatter 标 `origin: reference`（区别于 `origin: chat`）

对话收尾时输出**共识大纲**（5–8 行的骨架：标题结论 + 各节要点 + 不写什么的边界），用户确认后才动笔。

## 3. 动笔前：库上下文读取

吸附原生写作——让成文一次通过吸附流程：

1. 读 `00_系统/atlas/` 总 MOC 与相关域 MOC，确认该主题在库中的位置
2. 检索相关笔记（关键词匹配），明确本篇与它们的**分工**：补缺、深化、还是新主题
   - 发现与已有笔记高度重叠 → 停下来告诉用户：「库里的《xxx》已覆盖大半，建议改写那篇而不是新写一篇」——**宁愿不写，不造冗余**
3. 读 `00_系统/domains/<域>.md`：写作立场节 + **执笔与审查协议**（若有：开场必收、交付物格式）+ 时效性锚点
4. 无域档案 → 告知用户并按通用工程写作标准执行；有协议则优先按协议交付，不自由散文

## 4. 成文规范

- 遵守 vault 的原子笔记模板（`status: draft`、`origin: chat | reference`）
- 标题即结论，且结论必须与用户在对话中表达的判断一致——**不擅自升级或调和用户的立场**
- 体量遵守宪章规定（默认 800–3000 字）
- 自带挂载建议：文末列出建议的上级 MOC、建议互链的已有笔记（用 [[]] 语法）
- 不确定的事实显式标注 `[待核验]`（版本行为、性能数字、API/接口语义是重灾区），宁可标注不硬写
- 写法遵守域档案的写作立场节；用户对话中的个人表达习惯（口头禅式的判断句式等）保留——这是"独一无二"的质感来源
- 对人输出禁止 emoji

## 5. 交付与下一步

落盘 `10_inbox/` 后，向用户输出人话摘要：

```
初稿完成：《标题》
- 挂载建议：<域> 域，链接 [[A]] [[B]]
- 有 2 处 [待核验]（分别是……）
- 与库里《C》的分工：本篇讲实战，它讲原理

下一步建议：要我以审查模式过一遍吗？还是你自己先改？
```

**不自动进入审查**——写与审必须是两次独立调用（用户明确要求"写完直接审"时，也要显式切换姿态：清空执笔思路，以第一次阅读的姿态重读）。
