# 自定义与调教指南

给**克隆了本仓库、想按自己品味改**的人：前端有自己的防坑清单、老师有自己的教案标准、运营有自己的指标口径——都可以写进系统，让园丁和领域专家按**你的**标准干活。

日常只安装、不改包的用户：看根目录 [README.md](../README.md) 即可。  
单 skill 的安装与症状调优：[园丁说明](../skills/wiki-gardener/docs/使用说明与调优指南.md) · [专家说明](../skills/domain-expert/docs/使用说明与调优指南.md)。

---

## 1. 先分清三层：改哪一层、谁受益

| 层 | 位置 | 改了影响谁 | 升级 skill 会不会丢 |
|---|---|---|---|
| **A. 你的笔记库（优先）** | vault 里 `00_系统/宪章.md`、`00_系统/domains/*.md`、决策日志 | 只影响你的库 | **不会**（这是你的资产） |
| **B. 仓库里的种子（可选）** | `skills/wiki-gardener/assets/domain-seeds/`、`assets/personas/` | 影响「以后新建库」的默认预填 | 你 fork 后自己管；上游 `update` 可能覆盖若你改的是已安装拷贝 |
| **C. Skill 流程本体（少动）** | `SKILL.md`、`references/*.md` | 所有用这套 skill 的行为 | 需自己维护 fork，或把改动贡献回上游 |

**原则：有经验先写进 A（vault 域档案）。**  
domain-expert 读的是 vault 里的 `domains/`，不是每次去读 GitHub 上的种子。种子只是初始化时的「高起点拷贝」。

```
你的经验 / 防坑论
    → 写进 vault：00_系统/domains/前端开发.md（等）
    → 执笔与审查立刻变严、变像你
    → （可选）回写到 fork 的 domain-seeds，方便下一个空库
```

## 2. 推荐路径（有现成经验时）

### 步骤 0：正常装上并用起来

```bash
git clone https://github.com/tangzzz-fan/Wiki-Gardener-Skill.git
cd Wiki-Gardener-Skill
./scripts/install_skills.sh
```

对空文件夹说「运行 setup-knowledge-skills」，再「帮我初始化一个知识库」。  
选接近你的画像（如全栈 / 前端相关选「全栈工程师」再按需加前端域），把默认种子拷进 vault。

### 步骤 1：打开「你的」域档案（杠杆最大）

路径示例：

```text
<你的 vault>/00_系统/domains/前端开发.md
```

若初始化时没拷入：从仓库复制一份再改：

```bash
cp skills/wiki-gardener/assets/domain-seeds/前端开发.md \
   "<你的 vault>/00_系统/domains/前端开发.md"
```

### 步骤 2：把「自己的防坑论」写进固定四块

对照档案里已有结构，**优先加厚**这些节（比改 prompt 更管用）：

| 节 | 写什么（前端举例） |
|---|---|
| **专家立场 · 判断偏好** | 你一票否决什么：如「无 CWV 数据的性能结论不接」「状态方案必须先答归属」 |
| **领域 Smell 清单** | 你在 code review 里反复打回的模式：如「巨型 Context 当全局状态」「用 setTimeout 补竞态」 |
| **常见误区** | 团队新人容易信的错观念：如「上了 TS 就类型安全」 |
| **执笔与审查协议** | 开场必问什么、交付物要不要你们组的模板字段、红线（如禁止推荐已弃用 API） |

写作立场里的「偏好写法 / 避免写法」用来对齐文风（先结论后数据、必须附表等）。

改完不必重启装 skill：下次对 Agent 说「以前端专家审这篇 / 写这篇」，它读的就是你刚改的档案。

### 步骤 3：用「审一篇你熟悉的错文」校准

1. 故意放一篇带你讨厌味道的草稿进 `10_inbox/`  
2. 「以前端专家身份审一下」  
3. 看报告有没有打中你的 Smell；没打中 → **回写域档案**，不要怪模型「不够聪明」  
4. 决策日志里拒收/大改的理由，是最好的补档素材

这就是本库的调教闭环：**经验 → 档案 → 审查/执笔 → 再补档案**。

### 步骤 4：（可选）回写种子，服务「下一个空库」

若你希望下次初始化也带上这套标准：

1. 把 vault 里改好的 `前端开发.md` 同步回  
   `skills/wiki-gardener/assets/domain-seeds/前端开发.md`（在你的 fork 里）  
2. 跑校验：`python3 scripts/validate_skills.py && python3 -m pytest -v`  
3. 用 `REPO=./ ./scripts/install_skills.sh -g -y` 从本地重装，或继续 `npx skills update`（仅当你发布了自己的 fork）

**不要**把只属于某一公司的机密规范推进公开上游；私有 fork 或只留在 vault 即可。

## 3. 还能改什么（按常见需求）

### 宪章（品味与北极星）

- 文件：`00_系统/宪章.md`  
- 改：收录/排斥标准、「好笔记」定义、度量权重  
- 何时：Agent 总收你不想收的，或总拒你想留的  

初始化访谈已经在写这份；之后用决策日志里的拒收理由继续加厚。

### 画像 persona（新建库时的预填）

- 文件：`skills/wiki-gardener/assets/personas/*.md`  
- 改：默认加载哪些域、Atlas 分区名、访谈变体  
- 何时：你发现「全栈」预填总不对，想做「本公司前端」画像  

可复制一份 `全栈工程师.md` 改成 `本公司前端.md`，第零轮就会多一个选项（装的是你改过的包时）。

### 执笔/审查流程（少动）

- `skills/domain-expert/references/writing-mode.md`：追问清单、成文规范  
- `skills/domain-expert/references/review-mode.md`：severity、verdict  
- 何时：追问太烦/太少，或严重度分级和你体感长期不符——且确认不是域档案太薄  

改完后在 fork 里跑测试；全局安装用户需重装/update 你的包才生效。

### 园丁吸附与园艺

- `skills/wiki-gardener/references/intake.md`、`gardening.md`、`autonomy.md`  
- 何时：合并阈值、放权节奏、诊断指标锚点和你不一致  

同样：先看是不是宪章/域档案问题，再动流程文件。

### Companion 组合工作流（可选）

同包还提供内容思考 / 呈现类 companion（见 [`skills/README.md`](../skills/README.md)）。它们是**工具**，不改变园丁/专家职责：

| 阶段 | 可调用 | 产物落点 |
|---|---|---|
| 想清楚 | `grill-me`、`topic-resonate`、`content-diagnose`、`script-flow`、`content-decomposer` | 默认可进 `10_inbox/` |
| 成文入库 | `domain-expert` →（审过后）`wiki-gardener` 吸附 | inbox → `20_领域/` |
| 导出呈现 | `frontend-slides`、`ian-xiaohei-illustrations`、`gbro-cover-design` | **`90_export/`**（或你指定路径），不进吸附 |

短视频向仍遵守域种子里的**存在性先于形态性**：运营审核通过后再脚本/编导，再 inbox。  
调教 companion：优先改各包 `SKILL.md` / `references/`（fork 层），个人封面人脸等放 `gbro-cover-design` 本地 `config.md`（不入库）。  
完整唤起与落盘说明：[companion协作流程.md](./companion协作流程.md)。

## 4. 前端开发者速查（可照抄心态到别的域）

1. 初始化选工程向画像，按需加载 **前端开发**（及架构设计等）  
2. 打开 `domains/前端开发.md`，把你们组的：  
   - 性能预算（LCP/INP 红线）  
   - 状态管理约定  
   - 「禁止清单」（防坑论）  
   写进 Smell + 误区 + 协议红线  
3. 用一篇真实 PR 说明或错误笔记跑审查，直到报告语言像你们 TL  
4. 稳定后：要么只维护 vault；要么同步进自己 fork 的 `domain-seeds`

相邻域别抢戏：跨平台选型归 `跨平台开发`，大结构决策归 `架构设计`，本域专注前端交付与体验。

## 5. 自定义时的红线（避免把库改废）

1. **领域知识放 vault / seeds，不要写死进 `SKILL.md` 当唯一行业**（开源约定，也方便你多域切换）  
2. **产物仍进 `10_inbox/`**，不要让自定义协议改成直写 `20_领域/`  
3. **禁止 emoji**（人话卡片与文档）  
4. 改完 skill 包后跑：`python3 scripts/validate_skills.py` 与 `python3 -m pytest -v`  
5. 上游更新：若用官方 `npx skills update`，会刷新 skill 文件；**vault 不被覆盖**。你在已安装目录里手改的 skill 文件可能被冲掉——长期自定义请用 fork + 指向你的仓库安装  

```bash
# 从自己的 fork 安装示例
npx skills@latest add <你的GitHub用户>/Wiki-Gardener-Skill -g -y --skill '*'
```

## 6. 怎样算「调教成功」

- 同一类烂稿，审查连续打中你的 Smell，且误报变少  
- 执笔交付物字段符合你的卡片模板，很少再口头纠正结构  
- 新同事 / 未来的你，只靠域档案也能复现你的判断口径  
- 你几乎不再改 `SKILL.md`，只加厚 `domains/` 与宪章  

再往下的症状级调优表，见两份 skill 内的「后续调优指南」章节。
